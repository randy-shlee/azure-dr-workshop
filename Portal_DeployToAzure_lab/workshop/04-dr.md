# 04. Failover와 Failback

[이전](03-application.md) · [목차](README.md) · [다음: 정리](05-cleanup.md)

**이 문서는 Bash 버전입니다.** 각 서비스 화면에서 조작하려면 [Azure Portal 버전](04-dr-portal.md)을 사용합니다.
한 번의 전환·원복에서는 한 버전만 선택하고 두 절차를 동시에 실행하지 않습니다.

**실행 위치: 승인된 고정 출구 IP를 가진 지속 실행 Bash 터미널, 저장소 루트.**
[환경 안내](00-environment.md)에 따라 구독/config를 복원한 상태여야 합니다.
아래 스크립트는 Pod나 Automation 편집기, 포털의 JSON 입력란에서 실행하지 않습니다.
별도 `Failover.sh` 파일이 아니라 기존 `scripts/drill/10-failover.sh`를 재사용합니다.

이 단계는 실제 backend 역할을 변경합니다. 환경 소유자의 변경 승인을 받고 동시 쓰기를 중단합니다.
실제 전환·원복은 아직 실증하지 않았으며, RTO/RPO 보장이나 장애 주입 인증 절차가 아닙니다.

## 1. 첫 전환 전 확인

```bash
az account show --query '{subscription:name,id:id}' -o table
jq '{prefix,primaryResourceGroup,secondaryResourceGroup,globalResourceGroup}' "$CONFIG_FILE"
bash scripts/drill/00-precheck.sh
```

대상이 이번 실습인지 확인합니다. 첫 baseline에서 양 앱/서비스/샘플 완료, Storage Live 및 Planned 지원,
PG KRC writer/KRS replica, EH KRC synchronized pairing, TM 양 Online이 필요합니다.
오류면 진행하지 않습니다. 스크립트 성공만으로 앞 단계의 샘플·데이터 확인을 생략하지 않습니다.

## 2. KRS로 전환

```bash
unset CONFIRM
bash scripts/drill/10-failover.sh
```

확인 프롬프트에 화면의 **`FAILOVER <실제 prefix>`**를 입력합니다.
`CONFIRM` 환경 변수로 확인을 미리 우회하지 않습니다.

실행 순서는 **Storage Planned → EH alias KRS → PG KRS switchover → TM KRS 활성/KRC 비활성 → DNS·앱 데이터 확인**입니다.
Storage 전환은 수 시간이 걸릴 수 있습니다. 터미널을 유지하고 같은 명령을 중복 실행하지 않습니다.
터미널의 출구 IP가 허용되지 않으면 마지막 HTTP 확인이 실패할 수 있습니다. 이를 backend 전환 실패로 단정하지 않습니다.

## 3. KRS 응답과 데이터 확인

1. TM 앱의 응답 지역과 backend 지역이 KRS인지 확인합니다. DNS/브라우저 캐시가 남을 수 있습니다.
2. Storage 실제 primary와 PG writer가 KRS인지 확인합니다. EH alias active도 KRS여야 합니다.
3. TM 앱에서 **쓰기 → 읽기**로 동일 Blob/PG UUID와 EH send 결과를 기록합니다.
4. Redis/Search 실제 결과도 확인합니다. `-secondary` 샘플 조회를 전환 성공 증거로 대신하지 않습니다.

Bash에서 관리 상태를 조회할 수 있습니다. 아래 명령은 앞에서 불러온 공통 함수를 사용합니다.

```bash
storage_account | jq '{primaryLocation,secondaryLocation,failoverInProgress}'
pg_assert_pair secondary
bash scripts/eh-georecovery.sh status
```

EH는 **metadata-only Geo-DR**입니다. 전환 전 이벤트는 기존 KRC에 남으며 자동 복제·replay·offset 이식되지 않습니다.

## 4. KRC로 원복

```bash
unset CONFIRM
bash scripts/drill/20-failback.sh
```

**`FAILBACK <실제 prefix>`**를 입력합니다. Storage KRC → PG KRC → EH 현재 active 확인 → TM KRC 순서입니다.
명령이 정상 완료된 후 다음을 실행합니다. 오류가 났으면 후속 명령을 실행하지 말고 아래 중단 절차를 따릅니다.

```bash
bash scripts/drill/99-restore.sh
storage_account | jq '{primaryLocation,secondaryLocation,failoverInProgress}'
pg_assert_pair primary
bash scripts/eh-georecovery.sh status
tm_assert_online
```

`99-restore.sh`는 프로브/TTL 복구이며 backend 역할을 되돌리는 명령이 아닙니다.
이 과정에서는 fast 설정을 별도로 사용하지 않습니다.

## 5. 원복 후 상태 기록

TM 응답/Storage/PG는 KRC로 복귀하고 양 endpoint는 Enabled/Online이어야 합니다.
앱 쓰기·읽기와 Redis/Search/EH 접근을 다시 확인합니다.
**EH alias는 KRS에 유지됩니다.** 이전 KRC로 자동 failback하지 않으며 첫 전환 전 상태와 같지 않습니다.
`00-precheck.sh`나 `wait krc`를 다시 통과시키기 위해 기존 namespace를 삭제·재연결하지 않습니다.
다음 EH 보호 구성은 새 EMPTY namespace와 별도 변경 승인 작업입니다.

## 부분 실패 또는 연결 종료

반대 방향 스크립트나 전체 템플릿을 바로 재실행하지 않습니다. `$STATE_DIR/drill-log-YYYYMMDD.csv`의
마지막 START/END/ERROR, 실제 Storage/PG 역할, EH active, TM 상태부터 확인합니다.
Cloud Shell 연결이 끊겼다면 Azure 작업이 아직 실행 중인지 먼저 확인합니다.
unplanned 승격, 데이터 삭제, 기존 namespace 삭제로 우회하지 않습니다.

## 완료 조건

각 단계 UTC와 데이터 성공을 기록했고, KRC 앱·Storage·PG 복귀, EH KRS 유지, TM 양 Online을 확인했습니다.
실행하지 않았거나 실패한 단계는 그대로 기록하고 정리 여부를 결정합니다.
